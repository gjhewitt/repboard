## 2026-11-20 — Ruby security patch, and stopping Brakeman from breaking CI

**Shipped:**
- #59: RepBoard production now runs Ruby 3.4.13. Render emailed that a Ruby security release fixed a remote code execution bug, and my `.ruby-version` was still on 3.4.1. The PR bumped `.ruby-version` and fixed a stale `Dockerfile` that still said 3.2.1 (end of life).
- #61: Added `.github/dependabot.yml`. It checks weekly for new Brakeman releases and for updates to the GitHub Actions in my workflows. I limited the bundler updates to Brakeman so it doesn't open a PR for every gem.
- Turned on Dependabot alerts and security updates in the repo settings. Those cover every gem, but only open PRs when there's a known vulnerability.
- Cleaned up old gems on my Mac.

**Broke / got stuck on:**
- CI failed on the `scan_ruby` job. The log said `Brakeman 8.1.0 is not the latest version 8.1.1` and exited with code 5. My Ruby change had nothing to do with it.
- This was the second week in a row `scan_ruby` failed on a new Brakeman release (#48 last week, #59 today).
- After upgrading Ruby with Homebrew, every Rails command printed `ignoring rbs 4.1.2 / 4.1.3 because it is missing extensions`.

**How I solved it:**
- `bin/brakeman` runs with `--ensure-latest`, so CI fails any time a newer Brakeman exists. I ran `bundle update brakeman --conservative` (updates only Brakeman, nothing else), checked that `Gemfile.lock` changed by exactly one line, and pushed it as a second commit on the same PR. All four checks passed. I merged and confirmed the Ruby version in the Render build log.
- To stop it happening again, I added Dependabot instead of removing `--ensure-latest`. Removing the flag would stop the failures, but Brakeman could fall months behind without me noticing.
- The `rbs` warnings came from old copies in `vendor/bundle` that my lockfile doesn't use (it uses 4.2.0). `bundle clean --dry-run` showed them, along with old Rails 8.0 gems left over from last week's upgrades. Before running `bundle clean`, I checked that Bundler 2.6.5 (the version my lockfile needs) was still installed outside `vendor/bundle`. After the clean, the warnings were gone.

**Learned:**
- A red CI run doesn't always mean my change broke something. Read the log first.
- A patch bump (3.4.1 → 3.4.13) is security and bug fixes only, which is why this was low risk compared to the 4.0 upgrade that broke things before.
- If the same CI failure happens twice, fix the cause instead of fixing it by hand again.
- `bundle config get path` shows where Bundler installs gems. Mine is `vendor/bundle`, so `gem` commands don't see the gems my app actually uses.
- Preview before deleting. `gem cleanup --dry-run` showed it wouldn't have fixed the warning, which is how I found out the gems were somewhere else.
